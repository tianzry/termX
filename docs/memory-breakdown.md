# termX 内存分进程分解（Windows / release）

> 结论先行：内存的大头不在 Rust 主进程，而在 WebView2（Chromium）的多进程与其 renderer 里的 xterm.js 滚动缓冲。
> Rust + Tauri 只省掉了 Electron 的 Node/Chromium 主进程那一层，WebView2 仍然按 Chromium 的多进程模型跑，
> 所以「换成 Rust 就该低很多」并不成立；真正随会话增长的是 renderer 的 JS 堆（xterm buffer）。

## 测量方法

- 包：`src-tauri/target/release/termx.exe`（release，WebView2），经 `--remote-debugging-port=9222` 接 CDP。
- 进程：每 20 秒记录 `Win32_Process` 的 `WorkingSetSize` 与 `PrivatePageCount`，
  按 `--type=` 归类为 browser / renderer / GPU / utility，`termx.exe` 记为 main。
  **只统计 termx 进程树**（`termx.exe` 及其后代）；本机同时运行着另一个 WebView2 应用，
  若不按进程树过滤会把它的 browser/renderer/GPU/utility 一并算进来（30 分钟口径下约 +550 MB）。
- 前端：`performance.memory.usedJSHeapSize`、`document.getElementsByTagName('*').length`、
  xterm 诊断桩的实例数与 `buffer.active.length`（诊断入口仅在 `localStorage['termx.debug.xterm']='1'` 时暴露，默认关闭）。
- 场景：
  1. 空闲单窗口（无会话）。
  2. 单个 129 SSH 会话，持续输出 30 分钟（回滚 10000）。
  3. 129 + 本地 Git Bash 并行，各持续输出 30 分钟（回滚 10000）。
  4. 回滚 2000，重复场景 2。
- 说明：场景 3 中非当前标签的终端会被 fit 收缩成 5×10，缓冲行数虽到顶，但每行单元格数远小于可见的 39×117。

## 结论

### 内存花在哪

- **renderer**：单会话满 30 分钟占 33.0%（148.5 MB），并行两会话占 38.1%（197.3 MB）；
  其中 JS 堆 30 MB 左右，主要来自 xterm.js 的滚动缓冲（每行按单元格对象存）。
- **browser + GPU + utility**：单会话合计 256.9 MB（57.1%）、空闲 247.2 MB（63.3%），
  基本与是否有会话无关，属于 WebView2/Chromium 的固定底座；GPU 的私有字节还会高于工作集（驱动/纹理预留）。
- **Rust 主进程**：空闲 29.9 MB、单会话 33.3 MB、并行 33.7 MB，只占 6.5%~7.7%。
- **空闲基线**：390.6 MB 工作集、266.1 MB 私有；这是「打开就有的成本」。

### 为什么 Rust + Tauri 没把内存压下来

Tauri 用 Rust 替换的是 Electron 的 main 进程与 Node 运行时（那一层通常 100+ MB），
但窗口仍然由 WebView2 承载，而 WebView2 是完整的 Chromium 多进程架构：browser、renderer、GPU、
utility 一个都不少。termX 的界面逻辑、React 和 xterm.js 全在 renderer 里跑，
终端滚动缓冲又是 xterm.js 在 JS 堆里维护的单元格对象，所以「会话越长内存越高」的部分仍在 renderer。
换句话说，Tauri 省的是 Electron 主进程那一份，省不掉 Chromium 渲染栈；空闲 ~390 MB 是结构性成本。

### 回滚行数的实际收益与建议

同口径（单个 129 会话、持续输出 30 分钟）对比场景 2 与场景 4：

| 指标 | 场景 2（10000） | 场景 4（2000） | 差值 |
|---|---|---|---|
| 30 分钟总 WS 增量 | +41.1 MB | +8.4 MB | **−32.7 MB** |
| renderer 30 分钟增量 | +37.3 MB | +11.1 MB | **−26.2 MB** |
| JS 堆 30 分钟 | 30.3 MB（+21.3） | 13.7 MB（+4.8，峰值 16.0） | **−16.6 MB** |
| 缓冲行数 | 10039（15 分钟触顶） | 2039（5 分钟触顶） | −8000 |
| 触顶后曲线 | 15→30 分钟仍 +5.3 MB | 15→30 分钟 +1.4 MB，基本持平 | 收敛更快 |

换算到「每行成本」（用场景 2 的 9732 行增量做基准）：JS 堆约 **2.2 KB/行**，
renderer 工作集约 **3.8 KB/行**（场景 4 折算 2.8 / 6.4 KB/行，含固定漂移，取两者区间）。

**建议默认值：3000 行（即当前代码默认，不改成 10000，也不必压到 2000）。** 依据：

- 3000 行折算 30 分钟增量约 **+15 MB**（JS 堆 ~7 MB + renderer ~11 MB），
  比 10000 的 +41 MB 省约 26 MB，又只比 2000 的 +8 MB 多约 6 MB——2000 省下的量不值得损失 2/3 历史。
- 10000 行的收益为零：本场景 15 分钟就写满 10000 行，此后仍在涨，
  10000 只是把「触顶」推迟，长期最坏成本仍是每会话 ~40 MB；并行会话按会话数线性叠加。
- 3000 行在满速刷屏（本测试约 700 行/分钟）下留 4 分钟历史，正常交互式运维通常对应数小时；
  需要更多历史时由用户显式调高（5000 行 30 分钟约 +20 MB，可作为「愿意多付 5 MB」的选项）。
- 回滚不是内存主因：即使压到 2000，空闲基线仍是 ~390 MB，单会话 30 分钟仍有 +8 MB
  的结构性漂移；真正的大头是 WebView2 的 browser/GPU/utility 固定底座。
